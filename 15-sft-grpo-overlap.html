SFT-GRPO Data Overlap as a Post-Training Hyperparameter

Anonymous Authors
arXiv:2604.13515
April 2026
arXiv

This paper investigates a deceptively simple question with profound practical implications: when applying GRPO after SFT, how much should the SFT and GRPO training data overlap? Using Qwen3-8B as the base model, the authors systematically vary overlap from 0% to 100% and discover a monotonic degradation: 0% overlap yields 77.6% on Gaokao (vs. 61.8% SFT-only), while 100% overlap yields only 62.9%—essentially no gain over SFT alone. The paper introduces a dual-metric evaluation framework (compilation pass@k vs. semantic pass@k) and proposes the "reward saturation hypothesis" to explain why overlapping data neutralizes RL's benefit.

1. Research Overview

The standard post-training pipeline for modern LLMs follows a two-stage approach: SFT (Supervised Fine-Tuning) on demonstration data, then GRPO (Group Relative Policy Optimization, see Paper 14) on prompts with verifiable rewards. In practice, teams often use the same data pool for both stages—it's simpler and avoids the engineering overhead of maintaining separate datasets. This paper asks: is this convenience actually optimal?

The answer is a resounding no. Through controlled experiments with systematically varied overlap percentages, the paper demonstrates that data overlap between SFT and GRPO stages is not just suboptimal—it is actively counterproductive. The 100% overlap condition performs barely better than SFT alone, while the 0% overlap condition provides a massive +15.8 percentage point improvement. This finding has immediate practical implications for anyone building an SFT → GRPO pipeline.

🔑
Core Finding: Data overlap between SFT and GRPO stages is a critical hyperparameter that should be set to 0% (fully disjoint data pools). Overlapping data causes "reward saturation" where the model has already memorized the correct responses during SFT, leaving no room for RL to discover new strategies.

2. Experimental Setup

2.1 Base Model

The experiments use Qwen3-8B with thinking mode disabled. This is a deliberate choice: Qwen3-8B is a capable 8B-parameter model with a well-understood architecture (GQA, SwiGLU, RoPE, 128K context). Disabling thinking mode means the model generates direct responses without explicit reasoning chains, making the evaluation more sensitive to the training data's influence on response quality.

2.2 SFT Phase

The SFT phase trains on 20K instruction-response pairs sourced from four math-focused datasets:

Dataset Content Type Contribution
NuminaMath Mathematical problem solutions High-quality verified math solutions
Leanabell Formal mathematics (Lean) Formally verified proofs
HERALD Mathematical reasoning chains Step-by-step reasoning data
Lean Workbook Lean proof exercises Additional formal verification data

The 20K dataset size is deliberately moderate—large enough for the model to learn mathematical problem-solving patterns, but small enough that the overlap effect is clearly measurable. With larger SFT datasets, the overlap effect might be diluted (because the model encounters more diverse examples).

The dual-stage reward is critical: the hard compile gate ensures that the model learns to produce syntactically valid code, while the LLM judge provides a finer-grained quality signal for semantically correct solutions. This two-tier reward structure prevents the model from gaming the system by producing compilable but incorrect code.

2.4 The Overlap Variable

The paper's key independent variable is the overlap percentage between SFT and GRPO data pools:

Overlap % SFT Data GRPO Data Shared Prompts
0% 20K unique prompts 16K unique prompts 0 (fully disjoint)
30% 20K prompts 16K prompts (4.8K shared) 4,800 prompts
100% 20K prompts 16K prompts (all from SFT) 16,000 prompts

The 0% condition means the GRPO prompts are entirely new—the model has never seen these problems during SFT. The 100% condition means every GRPO prompt was already in the SFT data. The 30% condition provides an intermediate point.

2.5 Answer Injection Technique

A subtle but important detail: for GRPO prompts that overlap with SFT data, the paper uses answer injection—the correct answer is provided in the prompt to anchor the model's response generation. This ensures that the model can generate high-quality completions during GRPO sampling, even for problems it has already seen during SFT. Without answer injection, the model might generate poor completions for overlapping prompts, creating a confound between data overlap and generation quality.

3. Key Results

3.1 Main Results Table

SFT-Only (no GRPO) 61.8 58.2 — (baseline)
GRPO 0% Overlap 77.6 73.1 +15.8 C@1

"At 0% overlap, GRPO adds +15.8 percentage points over SFT alone—a massive improvement. At 100% overlap, GRPO adds only +1.1 points—essentially nothing. The entire benefit of RL is destroyed by data overlap."

3.2 The Monotonic Overlap Gradient

The results reveal a monotonic degradation: as overlap increases, performance decreases. This is not a threshold effect (where some overlap is fine but too much is bad) but a continuous gradient. Each additional percentage point of overlap reduces the GRPO benefit. This monotonic relationship suggests a fundamental mechanism rather than a statistical artifact.

3.3 Dual-Metric Evaluation

The paper introduces a critical evaluation distinction: compilation pass@k (does the code compile?) vs. semantic pass@k (does the code produce the correct output?). These metrics can diverge dramatically:

Overlap % Compile Pass@1 (%) Semantic Pass@1 (%) Compile-Semantic Gap
0% 92.3 73.1 19.2 points
30% 89.7 67.5 22.2 points
100% 85.1 59.8 25.3 points

The compile-semantic gap is revealing: even at 0% overlap, there is a 19.2-point gap between compilation correctness and semantic correctness. The model can produce syntactically valid code that produces wrong results. This gap widens with increasing overlap, suggesting that overlapping data not only reduces overall performance but specifically degrades the model's ability to produce semantically correct solutions.

📊
Dual-Metric Insight: The compile-semantic gap reveals that many "successful" GRPO outputs are actually failures—the code compiles but produces incorrect results. This distinction is invisible if you only measure compilation success, making dual-metric evaluation essential for code generation tasks.

4. The Putnam Amplification Effect

The paper tests the overlap effect on the Putnam competition dataset—a collection of extremely challenging undergraduate mathematics problems. On this harder benchmark, the overlap effect is even more pronounced:

At 0% overlap, GRPO provides a larger absolute improvement on Putnam than on Gaokao, because Putnam problems require more creative solution strategies that are less likely to be covered by SFT data. This "amplification effect" suggests that the benefit of disjoint data pools increases with problem difficulty: harder problems require more exploration during RL, and overlapping data constrains that exploration.

This has a practical corollary: for easy problems (where SFT data likely covers most solution patterns), the overlap effect is smaller. For hard problems (where SFT data covers few patterns), the overlap effect is larger. Teams should prioritize disjoint data pools especially when their target tasks include challenging problems.

5. Training Dynamics Analysis

The paper provides revealing analysis of training dynamics across overlap conditions:

5.1 Training Reward vs. Evaluation Performance

A striking finding is the inverse relationship between training reward and evaluation performance at 30% overlap. The 30% overlap model achieves higher training rewards during GRPO than the 0% overlap model, but lower evaluation performance. This apparent paradox is explained by the reward saturation hypothesis: the model optimizes for rewards on overlapping prompts (where it already knows the answers) at the expense of learning new strategies for novel prompts.

5.2 Reward Saturation Hypothesis

The paper proposes the reward saturation hypothesis to explain the overlap effect:

1. During SFT, the model learns the specific solution

4. GRPO cannot discover NEW solution strategies (patterns

   biased toward pattern A from SFT.

5. Result: GRPO "saturates" the reward signal on known
   patterns rather than exploring new ones.

In contrast, with 0% overlap:
- The model has NO prior knowledge of GRPO prompts
- It must explore freely during sampling
- GRPO discovers diverse strategies (patterns A, B, C, D)
- The group-relative advantages weight these strategies

This hypothesis connects to Paper 14's finding that online RL outperforms offline RL: the core mechanism is the same—exploration of new solution spaces. When data overlaps, the "online" aspect of GRPO is neutered because the model already has strong priors from SFT.

6. Qualitative Error Modes

The paper identifies three distinct error modes that emerge with increasing overlap:

Error Mode 1: Wrong Relationships

At high overlap, the model frequently produces code that correctly identifies the problem type but applies the wrong mathematical relationships. For example, it might recognize a problem as requiring integration but apply the wrong integration technique. This suggests that overlapping data teaches the model surface-level patterns (problem → technique association) without deeper understanding of why each technique applies.

Error Mode 2: Trivial Tautologies

The model produces code that is syntactically correct and compiles successfully, but the logic is tautological—it restates the problem rather than solving it. This is particularly common at 100% overlap, where the model has memorized the problem statement and can produce plausible-looking code that doesn't actually compute the answer. This error mode is invisible to compilation-based evaluation but captured by semantic evaluation.

Error Mode 3: Weakened Constraints

The model produces solutions that satisfy some constraints of the problem but violate others. For example, it might produce a correct answer but in the wrong format, or solve a simplified version of the problem rather than the full version. This suggests that GRPO on overlapping data causes the model to "cut corners"—optimizing for partial reward rather than full correctness. The dual-stage reward (compile gate + semantic judge) is specifically designed to catch this, but it cannot prevent it entirely.

7. Why 100% Overlap Fails

The 100% overlap condition deserves special analysis because it represents the most common (and most counterproductive) practice in alignment pipelines. When every GRPO prompt is also in the SFT data:

The model has already memorized the answers. During SFT, the model was trained on these exact prompt-response pairs. The optimal policy for these prompts is already learned. GRPO cannot improve on a policy that is already optimal for the training distribution.

Exploration is constrained. When sampling G outputs for a known prompt, the model tends to generate variations of the memorized response. The group-relative advantages within this group are small (because all outputs are similar), leading to near-zero gradient updates. GRPO effectively becomes a no-op.

The +1.1 point improvement is noise. The small gain from 100% overlap is likely attributable to minor distributional shifts (slightly different sampling temperatures, batch effects) rather than genuine learning. It is statistically indistinguishable from zero.

This connects to Paper 13's finding that DPO adds marginal value after strong SFT: the mechanism is identical. When SFT has already taught the model a behavior, preference-based optimization (DPO) or reward-based optimization (GRPO) cannot meaningfully improve it. The model has already converged to the optimal policy for the training distribution.

8. Practical Recommendations

8.1 Data Partitioning Strategy

1

Curate SFT Data

Collect high-quality instruction-response pairs for your target domain. This is your "demonstration" data—teaching the model what good responses look like.

2

Curate GRPO Data

Collect a SEPARATE set of prompts for RL training. These should be from different sources, problem types, or difficulty levels than the SFT data. Zero overlap.

3

Verify Disjointness

Check that no GRPO prompt appears in the SFT data (even approximately). Use fuzzy matching or embedding similarity to catch near-duplicates.

8.2 Source Diversity

The paper recommends sourcing SFT and GRPO data from different data sources entirely. For example: SFT data from curated textbooks, GRPO data from competition problems. SFT data from human-written solutions, GRPO data from synthetic problem generators. This natural disjointness ensures zero overlap without requiring explicit checking.

8.3 Monitoring Overlap in Production

In production alignment pipelines, data overlap can creep in accidentally (e.g., when curating new data from sources that partially overlap with existing data). The paper recommends maintaining a data fingerprint database—a hash-based or embedding-based index of all SFT prompts—to check for overlap before adding new GRPO data.

9. Limitations

⚠️
Limitations: (1) The study is limited to code generation with compiler-verifiable rewards—the overlap effect may differ for tasks without clear correctness signals. (2) The 20K SFT / 16K GRPO scale may not generalize to larger data regimes where overlap effects could be diluted. (3) The paper does not explore partial overlap (e.g., 5%, 10%) to identify the threshold where overlap becomes harmful. (4) The LLM judge (Gemini Flash 3) introduces its own biases in reward computation.

Task specificity. The code generation setting provides uniquely clean evaluation (compilation + semantic correctness). For tasks like creative writing, dialogue, or instruction following, where "correctness" is subjective, the overlap effect may be weaker because SFT and RL optimize for different aspects of quality.

Scale dependence. At larger SFT scales (e.g., 200K examples), the model may not memorize individual prompts as strongly, potentially reducing the overlap effect. The 20K scale is in the regime where memorization is likely, making the overlap effect pronounced.
