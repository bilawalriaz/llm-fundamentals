1. Overview: Why Unsloth for Preference Tuning?

Preference tuning—training models to prefer certain outputs over others—is the most practical alignment technique for individual researchers and small teams. While papers like Paper 10 (DPO), Paper 12 (ORPO), and Paper 14 (GRPO) provide the theoretical foundations, implementing these methods efficiently on consumer hardware requires significant engineering. Unsloth bridges this gap by providing optimized implementations that make preference tuning accessible on a single GPU.

The guide covers six preference tuning methods, each with different tradeoffs in terms of data requirements, computational cost, and alignment quality. Understanding when to use each method—and how to configure it optimally—is the core value of this document.

🎯
Key Value Proposition: Unsloth achieves 2× faster training and 60% less memory compared to standard HuggingFace trainers through custom CUDA kernels, fused attention operations, and optimized gradient checkpointing. For a 7B model on a 24GB GPU, this can mean the difference between fitting the model and running out of memory.

3. Complete DPO Code Example

The following is a complete, runnable DPO training script using Unsloth. Every configuration option is annotated with its purpose and the paper it connects to: 

# Complete DPO Training with Unsloth
# ===================================
# See Paper 10 for DPO theory, Paper 06 for LoRA

from unsloth import FastLanguageModel
from trl import DPOTrainer, DPOConfig
import torch

# ============================================
# STEP 1: Load Base Model with Unsloth
# ============================================
# Unsloth patches the model for 2× faster training
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3-8B",  # Or any supported model
    max_seq_length=2048,
    dtype=None,            # Auto-detect (bf16 for Ampere+)
    load_in_4bit=True,     # QLoRA: 4-bit quantization (Paper 07)
)

# ============================================
# STEP 2: Configure LoRA Adapters
# ============================================
# r=64: Rank of LoRA adapters (higher = more capacity)
#   Theory: Paper 06, Section 3 - LoRA rank determines
#   the number of trainable parameters per layer
#
# lora_alpha=64: Scaling factor (alpha/r = scaling)
#   When alpha=r, the adapter output is added directly
#   without scaling. This is the most common setting.
#
# 7 target_modules: All linear layers get adapters
#   q_proj, k_proj, v_proj, o_proj (attention)
#   gate_proj, up_proj, down_proj (MLP/FFN)
#   This is the "QLoRA" configuration from Paper 07
#
# lora_dropout=0: No dropout (Unsloth optimizes this)
#   Standard LoRA uses 0.05-0.1, but Unsloth's fused
#   kernels work better without dropout

model = FastLanguageModel.get_peft_model(
    model,
    r=64,                          # LoRA rank (Paper 06)
    lora_alpha=64,                 # LoRA scaling (alpha/r = 1)
    lora_dropout=0,                # No dropout (Unsloth optimized)
    target_modules=[
        "q_proj", "k_proj",        # Attention query/key
        "v_proj", "o_proj",        # Attention value/output
        "gate_proj", "up_proj",    # MLP gating
        "down_proj",               # MLP down-projection
    ],
    bias="none",
    use_gradient_checkpointing="unsloth",  # CRITICAL: 30% VRAM savings
    random_state=3407,
)

# ============================================
# STEP 3: Prepare DPO Training Data
# ============================================
# DPO requires preference pairs: (prompt, chosen, rejected)
# Format: {"prompt": "...", "chosen": "...", "rejected": "..."}

training_data = [
    {
        "prompt": "Explain quantum computing",
        "chosen": "Quantum computing uses qubits that can exist in superposition...",
        "rejected": "Quantum computing is about computers that are really fast..."
    },
    # ... more preference pairs
]

# ============================================
# STEP 4: Configure DPO Training
# ============================================
# DPOConfig replaces TrainingArguments in TRL

training_args = DPOConfig(
    # --- Core DPO Parameters ---
    beta=0.1,                    # KL penalty coefficient
    #   Theory: Paper 10, Section 3
    #   β controls how much the model can deviate from
    #   the reference policy. Lower β = more deviation allowed.
    #   β=0.1 is the ZEPHYR paper setting (default for most use cases)
    #   Range: 0.01-0.5, typical: 0.1
    
    loss_type="sigmoid",         # DPO loss variant
    #   "sigmoid": Standard DPO (Paper 10)
    #   "hinge": Hinge loss variant
    #   "ipo": Identity Preference Optimization
    
    max_length=2048,             # Max sequence length for pairs
    max_prompt_length=1024,      # Max prompt length
    
    # --- Training Hyperparameters ---
    output_dir="dpo-output",
    per_device_train_batch_size=2,
    gradient_accumulation_steps=4,  # Effective batch = 2×4 = 8
    
    learning_rate=5e-7,          # Lower than SFT (1e-5 to 5e-6)
    #   DPO uses lower LR to prevent destabilizing the
    #   alignment learned during SFT
    
    num_train_epochs=1,          # Usually 1-2 epochs for DPO
    #   More epochs risk overfitting to preference data
    
    warmup_ratio=0.03,
    lr_scheduler_type="cosine",
    
    # --- Unsloth Optimizations ---
    fp16=not torch.cuda.is_bf16_supported(),
    bf16=torch.cuda.is_bf16_supported(),
    optim="adamw_8bit",          # 8-bit Adam (saves memory)
    weight_decay=0.01,
    max_grad_norm=0.3,
    
    logging_steps=10,
    save_steps=100,
    save_total_limit=3,
    
    # --- Critical for DPO with LoRA ---
    remove_unused_columns=False,
    report_to="none",            # Disable W&B for local training
    
    # --- Reference Model Handling ---
    # ref_model=None: When using LoRA, the reference model
    # is automatically derived from the base model weights.
    # This saves ~50% memory compared to loading a separate
    # reference model.
    # See theory: Paper 10, Section 3 (KL divergence term)
)

# ============================================
# STEP 5: Create DPO Trainer
# ============================================
trainer = DPOTrainer(
    model=model,
    ref_model=None,              # CRITICAL: Use LoRA-derived reference
    #   When ref_model=None with LoRA:
    #   - The base model weights are frozen
    #   - The reference model = base weights (no LoRA adapters)
    #   - The policy model = base weights + LoRA adapters
    #   - This is equivalent to loading the same model twice
    #     but uses 50% less memory because the base weights
    #     are shared.
    #   See: Paper 06 (LoRA), Paper 10 (DPO reference model)
    
    tokenizer=tokenizer,
    args=training_args,
    train_dataset=training_data,
    dataset_text_field=None,      # Auto-detected from format
    
    # DPO-specific trainer arguments
    beta=training_args.beta,
    loss_type=training_args.loss_type,
    max_length=training_args.max_length,
    max_prompt_length=training_args.max_prompt_length,
)

# ============================================
# STEP 6: Train and Save
# ============================================
trainer.train()

# Save LoRA adapters (not full model)
model.save_pretrained("dpo-lora-adapter")
tokenizer.save_pretrained("dpo-lora-adapter")

# Merge and save full model (optional)
# model.save_pretrained_merged("dpo-merged", tokenizer)

4. Key Settings: Theory-to-Code Mapping

Each configuration parameter in the DPO code maps to a specific theoretical concept from the alignment literature. This section provides the complete mapping:

4.1 r=64 — LoRA Rank

The LoRA rank r determines the number of trainable parameters per adapter layer. From Paper 06: 

LoRA Parameter Count:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For a model with hidden dimension d=4096:
  Standard linear layer: d × d = 4096 × 4096 = 16.8M params
  
  LoRA adapter (rank r=64):
    A matrix: d × r = 4096 × 64 = 262K params
    B matrix: r × d = 64 × 4096 = 262K params
    Total: 524K params (3.1% of original)
  
  For 7 target modules × 32 layers:
    Total LoRA params: 7 × 32 × 524K = 117M params
    
  This is 0.7% of the 16B model's total parameters.

Why r=64:
  - r=8-16: Fast but limited capacity
  - r=32: Good balance for most tasks
  - r=64: High capacity for complex alignment tasks
  - r=128+: Diminishing returns, higher compute
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.2 7 Target Modules — QLoRA Configuration

The 7 target modules come from Paper 07 (QLoRA). Applying LoRA to all linear layers (not just attention) provides the most uniform adaptation: 

7 Target Modules (QLoRA from Paper 07):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Attention layers:
  1. q_proj  - Query projection   (d_model × d_head × n_heads)
  2. k_proj  - Key projection     (d_model × d_head × n_kv_heads)
  3. v_proj  - Value projection   (d_model × d_head × n_kv_heads)
  4. o_proj  - Output projection  (d_head × n_heads × d_model)

MLP/FFN layers:
  5. gate_proj - Gate projection  (d_model × d_ffn)
  6. up_proj   - Up projection    (d_model × d_ffn)
  7. down_proj - Down projection  (d_ffn × d_model)

Why all 7:
  - Attention-only (4 modules): Quick alignment, limited capacity
  - All 7 modules: Full model adaptation, better alignment quality
  - Paper 07 shows that applying LoRA to all layers improves
    performance by 2-5% over attention-only LoRA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.3 beta=0.1 — KL Penalty Coefficient

The beta parameter controls the strength of the KL divergence penalty in DPO. From Paper 10: 

DPO Loss with Beta:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

L_DPO = -E[σ(β × (log π_θ(y_w|x)/π_ref(y_w|x) 
                  - log π_θ(y_l|x)/π_ref(y_l|x)))]

Beta interpretation:
  β → 0: Model can deviate freely from reference
          (maximizes preference satisfaction, risks mode collapse)
  
  β → ∞: Model stays close to reference
          (conservative, ignores preference signal)
  
  β = 0.1: The ZEPHYR paper setting
          (moderate deviation, good general alignment)
          This is the most commonly used value in practice.

Beta variants from literature:
  β = 0.01: Very permissive (DPO-max)
  β = 0.1:  Standard (ZEPHYR, most papers)
  β = 0.2:  Conservative alignment
  β = 0.5:  Very conservative (rarely used)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.4 ref_model=None — The ORPO Insight

Setting ref_model=None in DPOConfig when using LoRA is the most important optimization for DPO on consumer hardware. This connects to a key insight from Paper 12 (ORPO): 

ref_model=None with LoRA:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Standard DPO (without LoRA):
  - Load model twice: policy model + reference model
  - Memory: 2 × model_size
  - For 7B model: ~28 GB (FP16) or ~14 GB (INT4)

DPO with LoRA (ref_model=None):
  - Base model weights are FROZEN (shared)
  - LoRA adapters are the only trainable parameters
  - Reference model = base weights (no adapters)
  - Policy model = base weights + LoRA adapters
  - Memory: 1 × base_model + LoRA adapters
  - For 7B model: ~8 GB (INT4) or ~4 GB (INT4 + Unsloth)

Why this works:
  - LoRA only modifies adapters, not base weights
  - The reference model needs the base weights without adapters
  - Since base weights are frozen, we can share them
  - The KL divergence is computed as:
    D_KL[π_ref || π_θ] ≈ D_KL[base_model || base_model + LoRA]
  
  This is EXACTLY what ORPO (Paper 12) does theoretically:
  ORPO eliminates the reference model from the loss function,
  making it equivalent to using a single model. When ref_model=None
  with LoRA, we achieve the same memory savings through weight
  sharing rather than loss function modification.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"The ref_model=None setting is the bridge between DPO theory and practical implementation. It achieves ORPO's memory efficiency within the DPO framework by exploiting LoRA's weight-sharing property."

4.5 use_gradient_checkpointing='unsloth'

Unsloth's custom gradient checkpointing saves approximately 30% VRAM compared to standard PyTorch gradient checkpointing, with minimal speed overhead. This is achieved through:

  • Selective checkpointing: Only the most memory-intensive operations are checkpointed, rather than all operations
  • Fused backward passes: Custom CUDA kernels fuse backward operations to reduce memory allocation overhead
  • Activation recomputation: Activations are recomputed during the backward pass instead of stored, trading compute for memory

5. ORPO Implementation

ORPO (from Paper 12) combines SFT and preference tuning into a single stage, eliminating the reference model entirely: 

# ORPO Training with Unsloth
# ==========================
# See Paper 12 for ORPO theory

from unsloth import FastLanguageModel
from trl import ORPOTrainer, ORPOConfig

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3-8B",
    max_seq_length=2048,
    dtype=None,
    load_in_4bit=True,
)

model = FastLanguageModel.get_peft_model(
    model,
    r=64,
    lora_alpha=64,
    lora_dropout=0,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                     "gate_proj", "up_proj", "down_proj"],
    bias="none",
    use_gradient_checkpointing="unsloth",
    random_state=3407,
)

# ORPOConfig (replaces DPOConfig)
# Key difference: no reference model at all
training_args = ORPOConfig(
    beta=0.1,                    # Same β as DPO
    max_length=2048,
    max_prompt_length=1024,
    
    per_device_train_batch_size=2,
    gradient_accumulation_steps=4,
    learning_rate=5e-6,          # Higher than DPO (single-stage)
    num_train_epochs=1,
    warmup_ratio=0.03,
    lr_scheduler_type="cosine",
    
    fp16=not torch.cuda.is_bf16_supported(),
    bf16=torch.cuda.is_bf16_supported(),
    optim="adamw_8bit",
    weight_decay=0.01,
    max_grad_norm=0.3,
    logging_steps=10,
    output_dir="orpo-output",
)

# ORPO Trainer (NO ref_model parameter)
trainer = ORPOTrainer(
    model=model,
    # NO ref_model — ORPO doesn't need it!
    # This is the key difference from DPO
    tokenizer=tokenizer,
    args=training_args,
    train_dataset=training_data,
)

trainer.train()
⚡
ORPO vs DPO Memory: ORPO uses approximately 50% less memory than standard DPO because it eliminates the reference model. When combined with Unsloth's optimizations, ORPO can train a 7B model on a single 16GB GPU, while standard DPO requires 24GB+.

6. KTO Implementation

KTO (Kahneman-Tversky Optimization) is designed for scenarios where you have binary feedback (good/bad) rather than paired preferences. This is common in real-world data: 

# KTO Training with Unsloth
# ==========================
# KTO uses binary feedback: (prompt, response, label)
# label: "good" or "bad" (not paired like DPO)

from unsloth import FastLanguageModel
from trl import KTOConfig, KTOTrainer

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3-8B",
    max_seq_length=2048,
    dtype=None,
    load_in_4bit=True,
)

model = FastLanguageModel.get_peft_model(
    model,
    r=64,
    lora_alpha=64,
    lora_dropout=0,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                     "gate_proj", "up_proj", "down_proj"],
    bias="none",
    use_gradient_checkpointing="unsloth",
    random_state=3407,
)

# KTO data format: binary feedback
kto_data = [
    {"prompt": "What is 2+2?", "completion": "4", "label": True},    # good
    {"prompt": "What is 2+2?", "completion": "5", "label": False},   # bad
    {"prompt": "Hello!", "completion": "Hi there!", "label": True},   # good
    {"prompt": "Hello!", "completion": "Go away.", "label": False},   # bad
]

training_args = KTOConfig(
    beta=0.1,
    max_length=2048,
    max_prompt_length=1024,
    per_device_train_batch_size=2,
    gradient_accumulation_steps=4,
    learning_rate=5e-6,
    num_train_epochs=1,
    warmup_ratio=0.03,
    lr_scheduler_type="cosine",
    fp16=not torch.cuda.is_bf16_supported(),
    bf16=torch.cuda.is_bf16_supported(),
    optim="adamw_8bit",
    weight_decay=0.01,
    output_dir="kto-output",
)

trainer = KTOTrainer(
    model=model,
    ref_model=None,              # Same LoRA optimization as DPO
    tokenizer=tokenizer,
    args=training_args,
    train_dataset=kto_data,
)

trainer.train()

KTO is based on prospect theory from behavioral economics: losses loom larger than gains. In the training context, this means the model penalizes generating "bad" responses more strongly than it rewards generating "good" responses. This asymmetry can be beneficial for safety alignment, where avoiding harmful outputs is more important than generating helpful ones.

7. HuggingFace TRL Integration

Unsloth integrates seamlessly with HuggingFace's TRL (Transformer Reinforcement Learning) library. All trainers (DPOTrainer, ORPOTrainer, KTOTrainer, GRPOTrainer) accept Unsloth models directly: 

TRL Integration Architecture:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Unsloth Layer:
  FastLanguageModel.from_pretrained()
    → Patches model with custom CUDA kernels
    → Optimizes attention (fused SDPA)
    → Optimizes gradient checkpointing
  
  FastLanguageModel.get_peft_model()
    → Adds LoRA adapters to all target modules
    → Configures gradient checkpointing='unsloth'

TRL Layer:
  DPOConfig / ORPOConfig / KTOConfig
    → Replaces TrainingArguments
    → Adds preference-specific parameters
    → Configures loss function
  
  DPOTrainer / ORPOTrainer / KTOTrainer
    → Handles data formatting
    → Manages reference model (when needed)
    → Computes preference loss
    → Calls Unsloth-optimized forward/backward

Flow:
  Data → TRL Trainer → Unsloth Model → Optimized GPU Kernels
  
  Key: The trainer handles the loss computation,
  the model handles the forward pass. Unsloth optimizes
  the forward/backward pass, while TRL handles the
  preference-specific logic.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

10. Practical Recommendations

10.1 Which Method to Choose?

1

Do you have preference pairs?

If YES → DPO (standard) or ORPO (memory-constrained). If NO → do you have binary feedback? → KTO.

2

Is your task verifiable?

Math, code, logic → GRPO (online RL with verifiable rewards). General tasks → DPO/ORPO/KTO.

3

Memory constrained?

T4 (16GB) → ORPO + QLoRA (4-bit). A10 (24GB) → DPO + QLoRA. A100 (80GB) → Full DPO or GRPO.

4

Starting from scratch?

Use ORPO (single stage, no SFT needed). Already have SFT model? Use DPO for preference alignment.

10.2 Common Pitfalls

  • Overfitting to preference data: Use 1 epoch, low learning rate (5e-7 for DPO), and monitor validation loss. DPO is particularly prone to overfitting.
  • Wrong beta: β=0.01 is too permissive (mode collapse). β=0.5 is too conservative (ignores preferences). Start with β=0.1.
  • Missing LoRA target modules: Using only attention modules (4 targets) instead of all 7 modules can reduce alignment quality by 2-5%.
  • Not using gradient checkpointing: Forgetting use_gradient_checkpointing='unsloth' wastes 30% VRAM for no benefit.
  • Loading ref_model unnecessarily: With LoRA, always set ref_model=None to save 50% memory.
