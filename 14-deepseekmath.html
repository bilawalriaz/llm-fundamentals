DeepSeekMath: Pushing the Limits of Mathematical Reasoning

Shao et al. (DeepSeek-AI)
arXiv:2402.03300
February 2024
arXiv

DeepSeekMath is a 7B-parameter model that achieves 51.7% on the MATH benchmark—competitive with models 10× its size—by combining a novel math data curation pipeline with Group Relative Policy Optimization (GRPO), a simplified reinforcement learning algorithm that eliminates the value function entirely. GRPO samples G outputs per prompt, computes group-relative advantages from their rewards, and uses an unbiased KL estimator—achieving PPO-level performance with dramatically reduced computational overhead. This paper establishes the foundation for modern RL-based alignment, and GRPO has since become the dominant RL algorithm used in Qwen3, DeepSeek-V2, and numerous open-source alignment pipelines.

1. Research Overview and Context

Mathematical reasoning has long been a benchmark for LLM capability because math problems require precise, verifiable reasoning chains—unlike open-ended text generation, a math solution is either correct or incorrect. DeepSeekMath addresses two fundamental challenges: (1) how to curate high-quality math training data at scale, and (2) how to apply reinforcement learning efficiently to improve mathematical reasoning beyond what SFT alone achieves.

The paper's significance extends well beyond math: GRPO provides a general-purpose RL algorithm that works for any task with verifiable rewards, and the insights about online vs. offline RL, process vs. outcome supervision, and code→math transfer have shaped the design of subsequent alignment pipelines including Qwen3's 4-stage post-training.

🎯
Key Contributions: (1) A scalable math data pipeline producing 120B tokens from web crawls. (2) GRPO algorithm that eliminates the value function from PPO. (3) Systematic comparison of RL paradigms (RFT, Online RFT, DPO, PPO, GRPO). (4) Empirical evidence that online RL, process supervision, and iterative training all independently improve mathematical reasoning.

2. The Math Data Pipeline

The first major contribution is a carefully engineered data curation pipeline that extracts mathematical content from web crawls. Math data is notoriously difficult to curate because mathematical expressions are often rendered as images, embedded in HTML tables, or mixed with non-mathematical text. DeepSeekMath's pipeline addresses this through a multi-stage filtering and classification approach:

2.1 Seed Selection and FastText Classification

The pipeline begins with OpenWebMath, a curated collection of mathematical web pages that serves as positive seed data. From this seed, a FastText classifier is trained to distinguish mathematical content from general web text. The classifier operates at the page level, scoring each page for mathematical relevance based on textual features (TeX notation, mathematical vocabulary, equation density).

The classifier is then applied to Common Crawl, the largest publicly available web corpus, to identify math-relevant pages at scale. This initial pass produces a large but noisy set of candidate pages that includes both genuine mathematical content and false positives (pages mentioning "formula" in non-mathematical contexts, for example).

2.2 Iterative Refinement

The pipeline then enters an iterative refinement loop consisting of 4 iterations:

1

Iteration 1: Initial Extraction

Apply FastText classifier to full Common Crawl. Extract pages scoring above threshold. Result: large but noisy dataset.

2

Iteration 2: Quality Filtering

Re-train classifier on high-confidence positives from Iteration 1. Remove low-quality pages (ads, navigation, boilerplate).

3

Iteration 3: Semantic Deduplication

Remove near-duplicate pages and pages with low mathematical content density. Focus on unique mathematical content.

4

Iteration 4: Final Curation

Final quality pass with tightened thresholds. Result: 35.5M pages containing 120B tokens of mathematical content.

2.3 Decontamination

The pipeline includes a critical decontamination step: pages containing text from benchmark test sets (MATH, GSM8K, etc.) are removed to prevent data leakage. This ensures that evaluation results reflect genuine reasoning capability rather than memorized solutions. The decontamination uses n-gram matching to identify and remove pages with significant overlap with benchmark problems.

"The final DeepSeekMath corpus contains 35.5M pages and 120B tokens, extracted through 4 iterations of classifier refinement from Common Crawl using OpenWebMath as seeds. This represents the largest curated math-specific training corpus at the time of publication."

3. Pretraining Details

DeepSeekMath is initialized from DeepSeek-Coder-Base-v1.5 7B, a code-specialized model. The pretraining then applies 500B additional tokens with a carefully designed data mix:

Data Source Proportion Description
DeepSeekMath Corpus 56% Curated math web pages (120B tokens)
AlgebraicStack 4% Algebraic computation data
arXiv papers 10% Scientific papers with mathematical content
GitHub code 20% Code repositories (retained from coder base)
Natural language 10% General web text for language modeling

The 56% math proportion is deliberately high—the model is being specialized for mathematical reasoning. The 20% GitHub code is retained because of the code→math transfer finding: code training improves mathematical reasoning. The structured, logical nature of code (conditionals, loops, function composition) shares deep structural similarities with mathematical proofs and computations. This finding has influenced subsequent models' pretraining data mixes, including Qwen3's 5T STEM/code stage.

💡
Code→Math Transfer Insight: The 10% arXiv component is notable because the paper explicitly finds that arXiv papers are ineffective for math reasoning—likely because arXiv content is primarily prose describing mathematical concepts rather than raw mathematical computation. Code, by contrast, directly exercises the computational reasoning patterns needed for math. This challenges the intuition that more math-adjacent data (papers) should help more than seemingly unrelated data (code).

4. GRPO: Group Relative Policy Optimization

GRPO is the paper's most influential contribution to the broader alignment community. It is a simplified variant of PPO that eliminates the learned value function entirely, replacing it with group-relative advantage estimation. This section provides the complete algorithmic treatment.

4.1 Motivation: Why Remove the Value Function?

PPO requires a learned value function (critic) that estimates the expected return from each state. Training this critic requires additional model capacity (often a separate neural network of similar size to the policy) and introduces training instability because the critic's own learning dynamics affect the policy gradient. For LLM alignment, the value function is particularly problematic because:

(a) The "state" in language generation is the entire sequence generated so far, making value estimation high-dimensional and difficult. (b) The reward signal is sparse (only at the end of a response), making credit assignment through the value function unreliable. (c) Training the critic adds significant compute overhead—roughly doubling the memory requirements of PPO.

4.3 Why Group-Relative Advantages Work

The key insight is that for each prompt, sampling G outputs creates a self-contained comparison set. Within this group, outputs that receive higher rewards are "better" and those with lower rewards are "worse"—regardless of the absolute reward scale. The group-relative advantage Â_i = (r_i - μ_G) / σ_G provides exactly this relative signal:

Outputs with above-average rewards get positive advantages (the policy is encouraged to produce similar outputs). Outputs with below-average rewards get negative advantages (the policy is discouraged from producing similar outputs). The normalization by group standard deviation ensures stable gradient magnitudes regardless of reward scale.

This is fundamentally different from PPO's value function baseline, which estimates the expected return from each position in the sequence. GRPO's approach is simpler, more stable, and requires no additional model parameters—making it the practical choice for open-source alignment where compute budgets are limited.

"GRPO achieves PPO-level performance with roughly half the compute, because it eliminates the value function entirely. For a 7B model, this saves approximately 7B parameters worth of memory and the associated training compute."

5. Unified RL Paradigm Comparison

One of the paper's most valuable contributions is a systematic comparison of six RL paradigms for LLM alignment, providing a unified framework for understanding their relationships:

Method Data Source Reference Model? Value Function? Reward Type Key Limitation
SFT Human demonstrations No No N/A (likelihood) Limited to demonstrated behaviors
RFT Filtered demonstrations No No Binary (correct/incorrect) Offline, limited exploration
Online RFT Model-generated, filtered No No Binary (correct/incorrect) Binary signal, no gradient weighting
DPO Preference pairs Yes No Pairwise preference Requires preference labels, offline
PPO Model-generated No Yes Dense reward Complex, unstable, expensive
GRPO Model-generated No No (group-relative) Dense reward Requires G samples per prompt

The key distinctions in this table are: (1) Online methods (Online RFT, PPO, GRPO) generate fresh samples each training step, while offline methods (RFT, DPO) train on fixed datasets. (2) GRPO eliminates both the reference model dependency of DPO and the value function of PPO, making it the most computationally efficient RL approach. (3) The binary reward of RFT/Online RFT provides less gradient information than the dense reward of PPO/GRPO.

6. Critical Empirical Findings

6.1 Online > Offline RL

The paper demonstrates that online RL methods consistently outperform their offline counterparts. Online RFT (which generates new responses each step and filters for correct ones) outperforms offline RFT (which trains on a fixed set of correct responses). This is because online methods continuously explore new parts of the solution space, discovering strategies that the offline dataset does not contain.

The magnitude of the online advantage is substantial: on the MATH benchmark, Online RFT achieves approximately 5–8 points higher accuracy than offline RFT, depending on the number of training iterations. This finding has profound practical implications: it means that the computational cost of generating new samples each step is justified by the performance improvement. This connects to Paper 15's finding that disjoint data pools are critical—if the RL data overlaps with SFT data, the online advantage diminishes.

6.2 GRPO > Online RFT

GRPO outperforms Online RFT despite both being online methods. The difference lies in the gradient weighting: GRPO's advantage-weighted gradient assigns larger updates to outputs with larger advantages, while Online RFT treats all correct outputs equally. This means GRPO can more efficiently learn from its best outputs while suppressing its worst, whereas Online RFT wastes gradient signal on mediocre correct outputs.

6.3 Process Supervision > Outcome Supervision

The paper compares two reward structures:

Outcome supervision: Reward = 1 if the final answer is correct, 0 otherwise. This is the simplest reward signal and requires only answer verification.

Process supervision: Reward = 1 for each correct intermediate step in the solution chain, 0 for incorrect steps. This provides denser feedback signal but requires step-level verification (which can be automated for math using proof assistants or step-by-step evaluation).

Process supervision consistently outperforms outcome supervision on the MATH benchmark, with the gap widening as the problem difficulty increases. The explanation is intuitive: for a 10-step proof, outcome supervision provides only a single bit of feedback (correct/incorrect), while process supervision provides up to 10 bits—one for each step. This dense signal enables faster and more targeted learning.

6.4 Iterative RL Helps

The paper applies GRPO iteratively: train → generate new samples → score → train again. Each iteration uses the improved policy from the previous iteration as the starting point, creating a virtuous cycle of improvement. The results show that 2–3 iterations of iterative RL provide significant gains over a single pass, but returns diminish after 3 iterations. This suggests that the policy converges to a local optimum within 3 iterations, and further gains require changes to the reward function or data distribution.

7. Why RL Works for Mathematical Reasoning

The paper provides an elegant explanation for why RL improves mathematical reasoning: it improves the majority vote accuracy (Maj@K) without significantly improving the pass@K accuracy. 

Maj@K = accuracy of the most common answer among K samples
Pass@K = accuracy of at least one answer among K samples

Observation: After RL training:
  - Pass@K stays approximately constant
  - Maj@K increases significantly

Interpretation: RL makes the model MORE CONSISTENT,
not more CAPABLE. It concentrates probability mass on
correct solutions, reducing variance without changing
the set of problems the model can solve.

This insight is profound: RL does not teach the model new mathematical skills. Instead, it calibrates the model's output distribution to favor correct answers over incorrect ones. The model already "knows" how to solve many problems (as shown by Pass@K), but it randomly explores incorrect solutions. RL reduces this exploration noise, making the correct answer the most likely one.

This connects to the broader understanding of RL as a distribution-shaping operation rather than a knowledge-adding operation. It also explains why SFT quality matters so much (see Paper 13): if SFT doesn't teach the model the correct solution at all, RL cannot recover it because Pass@K remains unchanged.

8. Experimental Setup

The evaluation setup is rigorous and designed to enable fair comparison across RL methods:

Parameter Value Justification
Training questions 144K CoT questions Large enough for stable RL training
Samples per question (G) 64 Large group size for stable advantage estimation
Max sequence length 1,024 tokens Sufficient for most math solutions
KL coefficient (β) 0.04 Weak KL constraint for maximum exploration
Learning rate 1×10⁻⁶ Conservative for RL stability
Clip ratio (ε) 0.2 Standard PPO clipping
Batch size 1,024 prompts Large batch for gradient stability

The choice of G=64 samples per question is notable: it provides a large enough group for reliable advantage estimation while remaining computationally tractable. For each training batch of 1,024 prompts, this requires generating 65,536 completions—computationally expensive but necessary for stable RL training.

10. Code Training Benefits Mathematical Reasoning

One of the paper's most counterintuitive findings is that code training improves mathematical reasoning. This is demonstrated through an ablation where models trained on code data show higher math performance than models trained on equivalent amounts of math-only data.

The explanation lies in structural similarities between code and mathematical reasoning:

Sequential logic. Both code and math proofs require following a sequence of logical steps, where each step depends on previous ones. Loop constructs, conditionals, and function calls in code mirror the case analysis, induction, and lemma application in math.

Symbolic manipulation. Code involves manipulating symbols according to rules (variable assignment, type conversion, operator precedence), which is isomorphic to algebraic manipulation in math.

Error correction. Debugging code requires identifying where a logical chain breaks down, similar to finding errors in mathematical proofs.

This finding has influenced pretraining data mix decisions across the field. Qwen3 allocates 5T tokens specifically to STEM and code in its second pretraining stage, and Phi-3 includes code data in its training mix. The code→math transfer insight also explains why the arXiv component (10% of pretraining data) is less effective than expected: arXiv papers describe mathematical concepts in prose, while code directly exercises computational reasoning.

11. Limitations

⚠️
Limitations: (1) GRPO requires G samples per prompt (G=64 here), making it computationally expensive despite eliminating the value function. (2) The findings are specific to math reasoning with verifiable rewards—generalization to tasks without clear correctness signals (creative writing, dialogue) is unproven. (3) The process supervision finding assumes automated step verification, which is available for math but not for many other tasks.

Compute cost of sampling. While GRPO eliminates the value function, it requires generating G outputs per prompt. With G=64 and batch size 1,024, this means generating 65,536 completions per training step—each requiring a full forward pass through the 7B model. For resource-constrained settings, this may be prohibitive even though GRPO is simpler than PPO.

Verifiable rewards only. GRPO's reward function relies on correctness verification (is the math answer correct?). For tasks without clear correctness signals—creative writing, instruction following, safety—the reward design is less straightforward. The paper does not address how to apply GRPO to these domains, though subsequent work (including Qwen3's General RL stage) has extended GRPO to broader tasks.

Model scale. The experiments use a 7B model. Larger models may exhibit different dynamics—particularly for the Maj@K vs. Pass@K analysis, where the concentration effect may be more or less pronounced depending on model capacity.

12. Practical Implications

12.1 For Alignment Pipelines

Use GRPO as the default RL algorithm. It is simpler than PPO, more effective than DPO for tasks with verifiable rewards, and has become the de facto standard in open-source alignment. See Paper 18 for practical GRPO implementation details.

Invest in online sampling. The online > offline finding is robust and consistent. Always generate fresh samples during RL training rather than training on fixed datasets.

Include code in math pretraining. The code→math transfer finding is actionable: include 15–20% code data in pretraining even if the goal is mathematical reasoning.

12.2 For Data Curation

Web crawl mining works. The DeepSeekMath pipeline demonstrates that high-quality math data can be extracted from web crawls at scale using iterative classifier refinement. The 35.5M pages / 120B tokens result is achievable with standard tools (FastText, Common Crawl).

Decontamination is essential. Removing benchmark data from training sets is critical for meaningful evaluation. The paper's careful decontamination ensures that the 51.7% MATH score reflects genuine capability.
